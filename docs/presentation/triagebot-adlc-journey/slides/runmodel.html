How a run works

Inside a terminal: one run, nine states

Sign-off

Escalated

a person takes over

Controls fail: agent retries, up to 3

Rework limit or age

A person closes every run: pass, rework, exception with a waiver, or terminate. Past the retry cap the run escalates. At sign-off or when escalated, people can edit the agent’s artifacts, and the controls run again.

Platform and agents drive it

A person must act

Walk the main row left to right: an event opens the run, the terminal’s agent builds the artifacts, the policy engine runs the spec’s controls, the reviewer agent recommends, and people sign off. Three side states: blocked only when a prerequisite is missing (a new event with the evidence reopens it; failing controls never block, they send the agent back to building), clarification when the agent needs an answer from a named role (the same run resumes, it is not a rework), and escalated when a limit is hit: the retry cap (timeline.max_auto_retries, 3 by default, shared by failed agent output, failed controls and interrupted steps), the rework limit, the run’s age, clarification rounds or SLA, or the token budget. At sign-off or escalated, an accountable or signing role can edit an artifact: a new version is saved, the controls re-run, and the human edit rate KPI counts it. Engineers: the states are RunState in orchestration/states.py (opened, blocked, building, awaiting_clarification, checking, reviewing, awaiting_sign_off, escalated, closed), and every transition is a recorded state change.
